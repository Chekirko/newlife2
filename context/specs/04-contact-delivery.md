# C1 — Надсилання контактної форми

Погоджено 2026-10-25: реалізувати справжнє надсилання на наявній `/contact` після merge PR #1 у master. Це продовження C1 з master-plan; нової сторінки чи зміни компонування немає.

- Поля: ім'я, email, тема, повідомлення. Серверна Zod-валідація, обмеження довжини, відхилення файлів/повторних полів і керівних символів у поштових заголовках.
- Серверний Action; адреса відвідувача тільки в Reply-To, одержувач визначається сервером. Повідомлення — звичайний текст, без HTML від відвідувача.
- Користувач обрав Resend (вже має акаунт для іншого проєкту). Одержувач — актуальний email сайту через getSiteSettings(), опційно серверний CONTACT_TO_EMAIL. From — CONTACT_FROM_EMAIL на підтвердженому домені, API key — RESEND_API_KEY.
- Захист від спаму: honeypot і спільні Redis-лічильники через Upstash REST EVAL: 5/IP та 3/email за 15 хв, 30/год на середовище. HMAC keys, TTL, без raw IP/email/текстів у Redis. Без Redis/config — fail closed, без in-memory fallback. Налаштування та межі — docs/contact-form.md.
- Успіх показується лише після підтвердження поштового провайдера (прийнято до відправлення, не гарантія inbox). При помилці текст зберігається для повторної спроби; мережеві помилки перехоплюються; кнопка блокується під час запиту.
- Видимі labels, autocomplete, field errors через aria-describedby/aria-invalid, доступні статуси; наявне компонування та бренд-кольори.
- Не зберігати звернення у Sanity, браузерному сховищі або application logs. Ключі — тільки серверні env; жодних реальних секретів у Git.
- Перевірка: цільові тести валідації/антиспаму/поштових помилок без реальних листів; lint, typecheck, pnpm test, pnpm run build; browser QA mobile/desktop. Реальну доставку можна підтвердити лише з налаштованим провайдером.
